# 备份导出提前拒绝恢复时冲突的 URL

日期：2026-10-03。本批仅处理服务成功生成、却因 URL 身份重复而无法恢复的版本化备份，不迁移或去重历史数据库。

## 确证问题

`items.url_hash` 可以为 NULL；历史库也可能保存与当前 URL 身份规则不一致的旧 hash。两个原始 URL（例如 `/page` 与 `/page#fragment`）在当前恢复规则下归一化为同一页面时，原先导出只验证每条记录，返回 HTTP 200、两条记录和有效校验和。把这个未经修改的服务备份直接提交恢复，恢复重新计算 URL hash，检测到重复并返回 422。

三个临时 SQLite、真实应用 API 探针证明：NULL hash 的重复 URL 和不同旧 hash 的重复 URL 都是 200 导出、422 恢复；NULL hash 的不同 URL 则正常往返。拒绝恢复时原有记录、向量、分析和修订号保持不变，本次没有证明恢复直接造成数据丢失。问题在于成功下载给用户造成备份可恢复的错误预期，尤其用户可能在下载后另行清空数据。

## 修复范围

`_read_backup_items()` 在每条记录通过 `IngestItem` 验证并转为 JSON 值后，调用与恢复写入相同的 `normalize_url()` 和 `sha256_hex()`，检查本次快照中是否已有相同 URL hash。验证先执行 `HttpUrl` 规范化，再执行应用的 URL 归一化，因而默认端口、主机大小写、片段、尾斜杠等边界与恢复一致。

出现重复时，在创建下载缓冲区之前返回固定的 HTTP 409 文本：`Stored records contain duplicate normalized page URLs; backup cannot be restored`。错误中不包含 URL、标题、正文、旧 hash 或密钥。它既不读取旧 `url_hash` 字段，也不修改数据库；输出中合法 URL 的既有展示值没有变化。

查重集合由原来的 10000 条上限约束，身份计算之后继续检查同一个准备预算。原有单行和总字节预算、SQLite 读取快照、进度处理器、超时、连接关闭、请求/导出配额、操作锁、鉴权和确认头保持原实现。恢复仍按原事务清空并写入，冲突仍返回 422 并回滚。没有改动 UI、备份版本或校验和算法。

## 回归证据

新增 `src/hyh/tests/test_backup_url_roundtrip.py` 共 10 项：

- 5 项拒绝：相同原始 URL、不同片段、尾斜杠、验证后的主机大小写/默认端口、缺省根路径；结合 NULL 或不同旧 hash。断言固定 409、无下载头/缓冲区、全部 SQLite 表及 schema 不变。
- 4 项成功对照：不同查询参数、路径大小写、HTTP/HTTPS、非默认端口，结合 NULL 或旧 hash。备份由真实 API 产生并检查校验和，再原样恢复、重新备份并比较全部页面字段。
- 1 项预算：身份计算期间预算耗尽，返回 503，原库不变。该项验证新增工作受原预算约束，不代表旧版有独立的预算漏洞。

所有用例检查连接已经关闭、操作锁与两种配额归还；随后执行真实新记录写入，验证未遗留读取快照阻塞。测试使用临时合成数据库及原有确定性的本地字符片段向量，没有个人数据、真实模型或外部 API。

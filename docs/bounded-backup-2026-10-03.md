# 备份下载生命周期修复（2026-10-03）

本批解决 `GET /data/backup` 在慢客户端下载期间持续占用数据操作锁的问题。没有修改前端、恢复格式、记录内容或备份容量。

## 修复前的证据

在独立临时 SQLite 中写入一条合成记录，用直接 ASGI 调用暂停备份的响应体发送：备份已经返回 `200`，但 `operation_lock` 仍被占用；另一个 `/items` 请求约 2.015 秒后返回 `503`。备份也没有占用已有的两个导出名额，因此普通导出与备份没有统一的快照数量限制。

## 现有备份合同保持不变

- 仍仅允许管理员下载；采集器密钥不能备份。
- 仍最多 10,000 条页面记录，最终 UTF-8 JSON 文件最多 20 MiB。记录数组预算和最终文件预算均保留，没有套用普通导出的 64 MiB 上限。
- 顶层仍为 `format,version,exported_at,items,sha256`；版本仍为 `1`，字段选择、记录顺序和 JSON 紧凑编码沿用原实现。
- SHA-256 仍由 `canonical_items(items)` 计算。恢复仍检查该摘要、版本、字段约束和用户确认头，备份没有包含密钥或派生分析数据。
- 媒体类型仍为 `application/json`，下载文件名仍为 `idm-pages-backup.json`。零记录备份也是有效文件。
- 超过记录/字节限制仍返回 `413`，不符合当前备份合同的旧记录仍返回 `409`，不会发送部分成功文件。

## 发送和取消

原有构建工作在同步线程中完成，包括数据库读取、模型字段校验、摘要和最终长度检查。数据库连接关闭后，完整 JSON 字节进入内存缓冲区，再复用普通导出的响应生命周期：

1. 成功响应开始时释放数据操作锁；慢备份下载期间可继续采集、删除或恢复。
2. 备份与两种程序化导出共享两个名额，从准备开始占用到发送结束。第三个下载请求返回 `503` 和 `Retry-After`，不会继续构建快照。
3. 响应体每块不超过 64 KiB，`Content-Length` 为完整 UTF-8 字节长度。发送阶段限时 30 秒。
4. 正常完成、ASGI 2.3 的 `http.disconnect`、ASGI 2.4 的发送异常、超时和任务取消都会关闭缓冲区并归还名额。
5. 如果准备线程尚未结束，请求取消会等待该线程完成后再清理结果和释放名额；重复取消不会把线程留在后台继续无名额工作。此行为由与普通导出共用的 `run_owned_sync` 实现。

已准备的备份保持自己的快照。其后的删除或恢复不会改写已经开始的下载，也无法撤回用户已下载的副本。

备份原先就会生成完整、最多 20 MiB 的 JSON，因此本批沿用内存缓冲区，没有再把私人浏览数据写入新的临时磁盘文件。这是文件大小限制，不是整个 Python 进程仅占用 20 MiB 内存的保证：准备期间仍有记录对象、编码和校验开销。本交付批次没有新增准备阶段期限；后续已在[准备预算批次](backup-preparation-2026-10-03.md)补上原始行预检、SQLite 锁等待和协作式截止，内存说明仍适用。

## 验证范围

`src/hyh/tests/test_backup_delivery.py` 使用临时合成数据库与真实 ASGI 应用，覆盖 21 个用例：格式与恢复往返、固定文件名及摘要、空备份、精确字节上限、记录上限和旧数据拒绝、慢发送中的采集/删除/恢复、两种导出与备份共享并发名额、断开/取消/超时清理、准备期间重复取消及线程失败、无权限不构建缓冲区，以及中文内容的多块输出与准确长度。

本批已执行备份专项与普通导出的合同、预算和发送四个测试文件：**96 项通过，65.04 秒**；保留一条既有 Starlette/httpx 测试适配器弃用提示。它们验证这次共用生命周期改动没有扩大导出容量或改变输出。

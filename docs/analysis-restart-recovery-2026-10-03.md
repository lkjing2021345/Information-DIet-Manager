# 重启后收敛遗留分析任务状态

## 真实进程复现

在本任务创建的隔离 Python 服务进程中，通过实际 HTTP 采集五条合成记录，再请求 `/analyze/run_full?force=true`。仅模型计算函数替换为可观察的阻塞桩；任务创建、提交、查询和服务进程锁均使用实际实现。确认任务已持久化为 `running` 后，终止这个测试进程，再用相同临时数据库启动未打桩的新服务。

修复前，新服务健康检查为 `200`，成功取得原数据库的进程锁，SQLite `integrity_check` 为 `ok`。但原先的合成 `queued` 任务和真实路由创建的 `running` 任务没有结束时间、没有失败原因；结果接口仍返回 `409` 和 `job not completed: running`。它们已没有可以完成工作的旧执行进程，状态却无限期保持进行中。

探针只终止自己创建的子进程，未读取个人数据库或加载真实模型。页面、向量、数据版本、分析历史与轻量统计在测试终止和重启间保持不变。该证据是 Windows 子进程强制终止后的一次任务状态恢复场景，不是断电、硬件故障或真实模型质量验收。

## 恢复合同

恢复只在 API 启动时执行，顺序为取得 `process_ownership`、初始化 schema、恢复遗留任务，随后才进入可服务的 lifespan。持有同一数据库锁的正常服务会阻止第二实例启动，因此第二实例不能借恢复操作修改第一个实例的活跃任务。

一个事务把遗留的 `queued` / `running` 更新为 `failed`，并写入固定安全原因 `Analysis was interrupted before this service start; run it again.`。`updated_at` 和 `finished_at` 记录本次确认中断的时间，不代表真实进程退出或计算结束时间；不据此推算 `duration_ms`。

其余列、已有完成或失败任务、未知历史状态和页面相关数据都保留。恢复不生成结果、不重跑任务、不修改已有模型和图表。重复启动不会再次改写已经恢复的失败任务。通用 `init_db()` 保持仅初始化结构的语义，恢复函数不放进普通查询或写入路径。

恢复事务失败则阻止启动成功并释放进程锁，避免返回健康状态后仍提供永久运行中的旧任务；修复存储问题后可以再次启动。未知缺列结构仍按初始化/SQL 错误失败，不自动猜测迁移方案。

## 证据边界

修复后重新运行同类真实服务进程探针，`queued` 与实际路由提交的 `running` 均恢复为 `failed`，固定错误匹配，两个时间字段位于重启检测时间窗内，结果接口明确返回 `job not completed: failed`。已完成/失败哨兵任务及业务表保持不变，第三次启动全部任务行保持不变；全部测试子进程已回收，临时数据库已清理。旧、修复后探针结果保存在本地被忽略的 `output/playwright/job-restart-20261003/`，不作为随仓库分发的制品或 CI 测试。

新增 `test_analysis_restart.py` **5 项回归通过**：全表数据与任务其他字段保持、API 结果、恢复幂等、实际 SQLite 更新中失败及提交失败、竞争子进程先拒绝、正常服务中的实际运行任务不被普通查询误恢复。独立复核连同三份历史结构和四项停服回归为 **12 项通过**。这些自动回归、真实进程探针和完整集成检查是不同层次的证据，重复运行不累加测试数量。

模型硬执行期限和可终止推理进程仍未实现；本批只能在服务重新启动后纠正持久化任务状态。它不能让当前挂起的线程自动退出，也不替代磁盘满、断电、所有时刻强杀或长期运行的恢复矩阵。完整回归、独立复查和精确提交 CI 另见 [质量状态](quality-status-2026-10-03.md)。

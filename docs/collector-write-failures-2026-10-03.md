# 合成数据收集器的写入失败与任务生命周期

日期：2026-10-03。范围为分类、情感两个独立训练数据收集器；不改浏览器采集扩展、首页、真实模型、调用预算或训练数据产品策略。

## 问题与修复

旧版 `_flush_pending_sync()` 在实际输出写入抛错后，仅增加失败计数并清空待写批次；`accepted_new_count` 已在缓冲阶段增加，因此 `collect()` 可以在没有输出文件时返回成功，并保存 `completed`。合成故障探针已复现两个收集器均存在该路径。直接让 flush 抛错还不够：派发器会吞掉任务异常，旧 done callback 会在结果读取前删除任务引用；若仅让 flush 抛错而保留待写批次，finally 仍可能再次尝试写入，不能局部加 raise 解决。旧故障探针证明了假完成和待写批次丢失，没有证明同一批次已被重复写入。此外，flush、sidecar 或初始加载失败可能跳过客户端关闭，两个原 CLI 的异常处理最终也返回成功退出码。

本轮按以下边界修复：

- 待写批次只预留目标容量。`accepted_new_count` 在 `DataStore.append_records()` 正常返回后才增加；`_remaining_target()` 同时扣除待写候选，避免缓冲阶段超过目标。正常结束只有确认数达到目标且缓冲为空才是 `completed`。
- 输出或进度保存失败以 `CollectorPersistenceError` 传播，保存首次错误的显式 cause，停止继续提交和追加。输出失败保留整个待写批次及 ID；部分写入结果可能不确定，因此不会自动清空、重放或声称全部写入失败。
- 派发器持有所有自己创建的任务，消费结果后才删除引用。持久化错误立即向上传播；退出时取消并等待未完成的自有任务，消费剩余结果，再关闭客户端。不会取消其他调用者的任务。
- 排队但尚未开始的 worker 在生成前检查停止状态；生成返回后先保留既有尝试计数，再检查是否继续处理。分类器在异步去重返回后、开始第二次模型标注请求前再次检查，避免其他 worker 写入失败后仍发起新请求。已经开始的调用依靠原有取消流程收尾。
- 从历史加载和初次进度保存起纳入生命周期保护。只在成功主路径末尾 flush；错误或取消清理不重放输出。`ModelPool.close()` 尝试关闭每个客户端，保留第一个错误，某个客户端失败不跳过后续客户端。
- 无错误且客户端关闭成功后才写正常终态；失败时尽力写 `failed`，取消时写 `interrupted`，侧车再次失败不覆盖原错。若存储介质本身持续失败，不能保证失败侧车已经落盘，此时内存状态和异常退出仍明确失败。
- 已停止的实例拒绝再次 `collect()`；需创建新实例从实际磁盘输出重新计算历史计数。这避免重用中断对象而意外重放保留批次。
- CLI 正常结束返回 0，普通异常返回 1，`KeyboardInterrupt` 或 `asyncio.CancelledError` 返回 130。失败使用 stderr JSON 的固定提示和异常类型；不打印异常原文或堆栈。argparse 的帮助/参数错误退出行为保持不变。

正常返回包括 `partial`：累计尝试预算耗尽但尚未达到目标时，CLI 仍可退出 0。
退出码 0 不表示目标已补满；调用方还需检查最终状态和实际输出计数。

## 验证

故障回归由独立代理编写，使用真实收集器、临时输出文件和 sidecar。部分生命周期案例替换派发器来控制写入或取消时点；任务归属、并发回收和停止边界案例使用真实派发器及受控模型调用。覆盖写前失败、部分字节写入后失败、正常收尾 flush 失败、启动/写后/终态进度失败、坏 JSON 历史、输出首错叠加进度及关闭次错、每个客户端关闭尝试、真实 `Task.cancel()`、并发任务回收、快速完成时的精确目标，以及两个真实脚本入口的退出码和输出通道。

- 作者首次联合故障、恢复及追加格式回归：**213 passed / 9.03 秒**（当时故障回归为 48 项）。
- 增补双 CLI 取消边界后，独立故障及恢复回归：**68 passed / 8.05 秒**（50 项故障 + 18 项恢复）。
- 在原故障案例内补齐停止实例重用后不重放、不增加确认计数的断言；补充停止边界检查前，作者对故障、恢复和追加格式联合执行为 **215 passed / 11.07 秒**（50 + 18 + 147）。
- 独立复查进一步发现：即使派发器停止提交，已排队 worker 仍可能开始生成，分类器也可能在去重 await 后开始新标注请求。新增 `test_collector_stop_boundary.py` 使用真实派发器和真实 `_process_spec`，只替换模型调用/质量过滤/语义去重；修复前 **3 failed / 0.79 秒**，两个生成入口及分类器标注入口均观察到第二次调用在 fatal 标记为真时开始。
- 加入上述检查后，最终产品源码于北京时间 **10:22:44** 冻结；作者最终联合回归为 **218 passed / 11.76 秒**（3 + 50 + 18 + 147）。该冻结之后的整套回归、独立复查和精确提交 CI 由主任务记录。

所有生成调用均为替身，没有支付远程调用、下载模型或读取个人浏览数据库。取消回归是 Python 异步任务取消，CLI 中断为受控异常，不等同于 Windows 控制台信号、系统崩溃或断电验收。

## 保留的边界

这批不实现跨格式原子追加、`fsync` 耐久性、跨进程写锁或损坏尾部自动恢复。append 正常返回只表示当前调用正常完成；写入后、flush/close 或替换时抛错，磁盘可能已经变化。失败批次保留在当前对象的内存中，不自动导出到额外文件，也不把 sidecar 当作实际记录的替代来源。

`generated_count` 和各候选分布仍包含曾接受到缓冲的候选，不能解释为全部已持久化；是否达到输出目标由确认计数及磁盘恢复基线决定。底层生成器既有模型日志、模型池构造中途失败，以及不响应取消的模型/客户端仍是独立审查范围；本轮没有增加任意硬超时或资源限额，也不承诺任意重复取消或强杀下的清理完成。

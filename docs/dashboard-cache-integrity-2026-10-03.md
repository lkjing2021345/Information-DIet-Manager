# 图表缓存复用完整性：2026-10-03

## 已确认问题

固定时间窗口的图表 API 在复用 `analysis_jobs` 已完成任务时，原先只检查 JSON 可读、`analysis_status` 为 `ready` 且没有警告。将真实临时 SQLite 中该任务的结果改成有限 JSON `{"analysis_status":"ready"}` 后，第二次 HTTP 请求仍返回 `200`、`cached: true`，并新增一条完成任务；必要的窗口、覆盖率和图表字段都已缺失，也没有重新调用合成分析流水线。这证明缓存状态可以掩盖结果结构损坏。

当前界面的显式分析请求仍使用 `force=true`。上述问题来自不强制重算的 API 缓存路径，不能据此声称已经观察到页面展示错误图表。

## 本次修改

仅在当前 `schema_version: 3` 图表缓存复用前增加检查：

- 窗口必须对应本次数据库快照，输入、处理、可用数量及截断标识一致；覆盖计数必须是有界整数，布尔值不算数量。
- 当前图表的全局字段、分类、别名、日期和每日统计字段必须存在且类型正确。计数、分布和曲线之间检查必要的总量与包含关系。
- 分类、情感和相邻比较仍各自允许没有有效结果；零值保留。没有对应测量时，均值或比例必须为 `null`，有有效测量时必须为范围内有限数；不借缺失值生成零测量。
- 不合格缓存沿原有流程重新计算，原历史行保持原样。重新计算不可用或失败时，响应保持 `unavailable` / `failed`，新任务标为失败，不退回坏缓存。

没有变更指标计算公式、模型调用流程、通用历史 JSON 读取、前端请求或样式，也没有迁移、覆盖历史记录。

## 本地证据

新增 `test_dashboard_cache_integrity.py` 使用真实 FastAPI HTTP、临时 SQLite 和合成 DataFrame：

- 首轮旧实现 **36 failed / 9 passed**：34 种结构、类型或计数损坏和 2 种重算失败被缓存掩盖；合法缓存及强制重算对照通过。
- 自查追加“分类计数存在但分类曲线为空”一项，初版校验仍失败，补齐仅允许缺时间记录不进入日曲线的计数下界后通过。
- 独立复查在 Windows 发现初版检查使用 `datetime.fromtimestamp`，对 API 允许的 `253402300799999` 毫秒上界抛出 `OSError`：首次请求正常生成，二次复用却返回 500。补充真实 API 的完整日期范围、1970 零边界、9999 上界和跨日四项后，修复前 **2 failed / 2 passed**。转换已改用与实际聚合器相同的 UTC epoch 加 `timedelta`，不依赖平台时间戳转换范围。
- 最终新文件 **50 项**，连同原图表、历史完整性和指标测试共 **165 passed / 1 warning，19.29 秒**。四项日期边界额外核对缓存前后的图表、窗口与生成时间一致。既有 Starlette/httpx 适配器弃用提示保留。
- 合法缓存对照包含分类、情感、相邻比较、极性独立缺失，全部缺失、混合部分覆盖、真实零值和窗口截断；命中时禁止任何额外流水线调用。坏缓存重算后再次请求可正常复用新结果。

这些是本地合成模型接线和持久化回归，不代表真实模型推理准确率、浏览器端到端验收或精确提交的远端 CI；集成结果由主流程另行记录。

## 边界

这是一道缓存复用检查，不是所有历史报告的业务 schema 迁移，也不验证模型结论是否真实。结构与计数自洽的数据仍可能含错误的模型判断；本次没有通过重跑模型来验证每个缓存测量。直接历史读取继续使用原通用 JSON 合同，未增加本次图表专用限制。合法历史编码兼容保持原样。

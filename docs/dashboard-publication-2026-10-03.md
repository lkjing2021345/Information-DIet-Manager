# 仪表盘分析发布失败的任务状态修复

## 问题与修复

仪表盘分析先提交 `running` 任务，再在独立事务保存结果。原发布更新发生 SQLite 错误或 JSON 编码错误时，请求返回 500，但此前的任务可能一直保留 `running`；处理线程已经退出、分析名额也已释放。另有非有限数值或过深结果未经发布前校验进入历史。

现在发布使用保存点，先将结果转换成严格 JSON，再执行已有的有限值、UTF-8 和深度检查。转换保留原有 JSON 行为：小时分布在 Python 中使用整数键，在线响应和持久化 JSON 中仍是字符串键。没有修改图表、模型、窗口选择或计算规则。

校验或写入失败时，回滚结果及触发器的部分修改；数据库仍可写时，保存 `failed`、结束时间和固定错误，返回 500：

```json
{"job_id": 1, "status": "failed", "detail": "Visualization analysis failed; no valid result was produced."}
```

若 SQLite 已回滚整个事务，原保存点也不存在：重新取得写事务、再次验证数据库版本和任务仍在运行，才保存失败状态。删除或恢复引起的快照过期仍返回 `409 analysis_snapshot_expired`，不能被普通发布失败处理吞掉或重建已删除任务。

原 `_failed_full_response` 改名为 `_failed_analysis_response`，由完整分析与仪表盘共用；完整分析原有调用的行为不变。

## 验证

新增 `src/hyh/tests/test_dashboard_publication.py` 使用真实 ASGI、临时 SQLite 和合成数据：

- SQLite `RAISE(ABORT)`、`RAISE(FAIL)` 和 `RAISE(ROLLBACK)`；其中 FAIL 保留部分语句效果，验证回滚边界，ROLLBACK 验证保存点失效后的恢复。
- NaN、孤立代理字符、非 JSON 对象和深度超限不能留下成功结果或悬挂任务。
- 已过期版本与已删除任务仍为 409；数据库连失败状态也拒绝写入时，不伪称失败状态已经持久化。
- 正常空窗口、五条合成记录的 ready 结果、小时键和后续缓存命中保持一致；不加载真实模型。

最初十项在修复前实测 **6 失败、4 通过**。第一次加入直接 Python 对象校验时，联动回归发现合法整数小时键被拒；已改为校验 JSON 表示，并加入 ready/缓存对照。修正后的四文件定向联动为 **122 通过、1 项已有 Starlette 弃用警告**（26.96 秒）。之后补充的事务整体回滚用例在保存点版本中实测失败；完成恢复分支后，最终新增文件 **12 项全部通过、1 项同类警告**（2.19 秒）。这两组结果对应不同验证范围，不合并计数。

## 保证边界

本批修复仪表盘新结果的发布阶段，不改变取消合同、缓存读取策略或推理执行方式。数据库无法重新取得写事务、拒绝失败状态更新、回滚或提交自身失败时，仍可能无法记录终态；固定 500 不等于失败记录必然落库。启动时的中断任务恢复机制保留。

本报告不代表真实模型推理、浏览器交互、完整项目回归或精确提交 CI 已验收；这些由本批统一发布检查单独记录。

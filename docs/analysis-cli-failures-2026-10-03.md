# 分析 CLI 的失败通道与退出码

## 已确认的问题

统一分析命令有三个源码入口、五种常用启动方式：仓库根目录或外部目录运行 `scripts/run_analysis.py`，直接运行旧脚本，旧模块入口与 `src.analysis_engine.main` 模块入口。

旧版仅在旧脚本的 `__main__` 捕获异常，且把 `str(exc)` 写入 stdout；两个转发入口直接调用 `main()`，未捕获的异常及堆栈写入 stderr。通过真实 pandas 读取临时合成 CSV 后注入含输入标题、异常细节和合成密钥的 `RuntimeError`，五种启动方式均暴露了这些标记。另用真实 JSON 输入里的非数字 `options.batch_size`，无需依赖故障注入即可观察到原始选项值进入异常输出。

旧版两个 legacy 启动方式捕获 `KeyboardInterrupt` 后正常返回，退出码为 **0**，会让调用脚本误判分析成功。其他三个启动方式未捕获该异常，在本机 Windows 子进程中得到非零系统退出码并输出堆栈。

这些证据针对失败输出，不把用户明确要求输出的成功分析 JSON、报告正文或记录内容算作日志泄漏。故障中的密钥是合成标记，不是生产模型收到能力密钥的证据。受控抛出的 `KeyboardInterrupt` 验证 Python 异常边界，不代表已测试 Windows 控制台信号传递、终止整个进程树或模型硬超时。

## 实现

`src/lsj/src/main.py` 新增 `cli_main()`，三个源码入口统一通过 `sys.exit(cli_main())` 启动：

| 场景 | 退出码 | 输出 |
| --- | --- | --- |
| 正常完成 | 0 | 保留原成功结果和文件输出行为 |
| 普通执行异常 | 1 | stderr JSON，固定操作提示和异常类型 |
| `KeyboardInterrupt` | 130 | stderr JSON，固定中断提示和异常类型 |
| argparse 帮助或参数错误 | 0 / 2 | 保留 argparse 的原有行为 |

失败 JSON 的字段为 `success: false`、`error`、`error_type`。不插入异常原文，不输出异常堆栈，不向 stdout 添加失败结果。`main()` 仍是原来的直接调用接口：直接调用者会收到原始异常对象；两个转发模块也保留 `main` 导入，供原有导入调用方式继续使用。

本批没有改动算法计算、模型下载策略、训练日志、收集器、前端或数据库。底层模块在失败前自行写出的日志不由 CLI 外层追溯清除，因此不能据此宣称全部模型日志已经安全。本批也不承诺中断时撤回已经写出的文件或回滚所有副作用。

## 回归证据

新增 `src/lsj/tests/test_cli_failures.py` 共 **22** 项：五个实际入口各测试普通失败、中断、成功输出和真实 JSON 选项错误；另两项检查直接调用仍抛出原异常对象。CSV 故障和成功测试通过 `runpy` 执行实际入口文件，模型相关导入被显式阻断，成功评估使用受控替身；另外五项 JSON 错误测试直接执行脚本或 `python -m` 命令，不注入异常。不加载真实模型、不下载依赖、不读取个人浏览数据库。

- 旧代码运行最初 17 项新增回归：**10 failed，7 passed，12.57 秒**。失败分别对应五个入口的普通异常通道/内容与中断退出码；五个实际命令的自然 JSON 输入错误也已在旧版探针中复现。
- 修复后最初 17 项新增回归加已有 CLI 入口测试：**41 passed，15.60 秒**。既有测试覆盖 argparse 帮助、非法参数、无可选依赖启动、JSON/CSV 接线及输出格式转发。
- 追加五项无注入 JSON 输入回归后，22 项新增 CLI 测试、24 项既有入口测试与 18 项收集器恢复独立复查合计 **64 passed，21.88 秒**。
- `git diff --check` 通过。

完整 Python 回归、浏览器证据和精确提交的 GitHub CI 结果由本轮总验证另行记录。本批局部测试是命令行行为验收，不是实际模型质量验收。

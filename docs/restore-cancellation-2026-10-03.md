# 恢复请求取消与事务归属（2026-10-03）

## 已复现的问题

`POST /data/restore` 原先直接等待 Starlette 的 `run_in_threadpool(replace)`。原始 ASGI 请求任务被 `asyncio.Task.cancel()` 取消后，该等待可以立即结束，但 Python 无法随之停止执行 SQLite 替换事务的线程。中间件因此提前释放数据操作锁和请求名额，线程随后仍可能提交恢复。

临时数据库探针先保存两条记录，备份第一条，暂停恢复事务后取消请求。取消前操作锁为占用、可用请求名额为 3；取消后请求已结束、线程仍运行，但操作锁已释放、名额恢复到 4。接着结束 lifespan，可以重新获取数据库的 OS 所有权锁；释放后台线程后，记录数才从 2 变为 1。问题是后台写入脱离了请求的资源归属，不能据此认定发生了普通浏览器断连或数据库损坏。

## 最小修复

恢复端点改用项目已有 `run_owned_sync(replace)`。即使请求被重复取消，也会等待线程的事务提交或回滚以及连接关闭，然后才传播取消，让中间件释放门闩和名额。正常响应、替换确认、校验和、重复 URL 检查及原子回滚合同不变。

取消请求不承诺撤销用户已经授权的恢复：若工作线程成功，事务仍完成；若工作线程异常，则原事务回滚。修复保证事务结束前请求仍保有资源归属，不在不确定时机尝试强制停止 SQLite 线程。

## 验证

新文件 `src/hyh/tests/test_restore_cancellation.py` 使用真实 ASGI 应用、真实 SQLite 事务和临时合成数据。暂停点在事务已写入首条 embedding 后，验证其他连接看不到部分替换；覆盖不取消、一次取消、三次取消，分别在工作线程成功和失败时运行；另验证服务先等待请求退出、再结束 lifespan 的过程中，事务连接先关闭，随后才释放实际 OS 所有权锁。

- 修复前：新增测试 **6 failed，2 passed**。6 个取消场景均确证线程未结束时请求已提前结束。
- 修复后：`test_restore_cancellation.py`、`test_local_security_and_data.py`、`test_backup_delivery.py` 合计 **86 passed**。
- 一条既有警告：Starlette 提示其 TestClient 使用 httpx 的兼容方式已弃用；与本次事务修复无关。

运行环境是项目隔离的 Windows CPython 3.12 锁定测试环境。未访问个人数据库，也没有模拟杀死操作系统进程；drained shutdown 测试只核验“先等待请求退出，再结束 lifespan”的顺序。真实浏览器恢复验收不能由本组测试替代。

仍有明确边界：服务若在优雅停服超时后取消请求并直接执行 lifespan shutdown，而不继续等待请求，仍可能提前释放数据库所有权；锁定版本 Uvicorn 的该超时路径属于这种情况。本次没有增加全局工作线程登记和停服 drain，不能声称实际服务的超时停服已得到保证。另以临时数据库只读探针确认 `collect`、`import`、`delete_all`、`delete_item`、`analyze/run` 五个普通同步写路由仍有相同的取消后门闩提前释放问题；本批未扩展修改这些路由。

后续批次已补齐上述普通写入及摘要 GET 路由，并增加每个 lifespan 的工作登记与停服等待；后续结果见 [写入取消](write-cancellation-2026-10-03.md) 和 [停服所有权](owned-shutdown-2026-10-03.md)。本页的 8 项早期测试仍只证明其明确描述的请求排空顺序，不能替代后续 Uvicorn 超时路径验收。

# 第三轮：本机权限、数据生命周期与恢复验收

日期：2026-09-24。基线：`c2cd590605a5212c0f0d155ef456d474a08ea90a`。目标仍是每人本地运行的 Windows + Chrome 开源开发预览。

## 本轮交付

这一轮完成了本机服务的权限边界，以及“备份 → 删除 → 恢复”的页面记录管理闭环。实现后再次检查了并发、失败回滚、凭证存储、客户端旧响应和升级路径，发现的问题修复后重新验收。本轮没有将真实模型推理或企业级发布就绪列为已完成。

| 领域 | 修改后的行为 | 验证证据 |
| --- | --- | --- |
| 未授权读取/写入 | 除最小 `/health` 外均需 Bearer；管理/采集两类权限 | 未授权路由、越权、查询/Cookie 密钥无效测试 |
| 浏览器与网络边界 | 精确 Origin、Host、实际回环对端；受限 CORS | DNS rebinding 主机、外站/null 来源、扩展预检、远程对端测试 |
| 凭证与默认数据目录 | 两把独立随机密钥、私有文件、日志只含路径；默认数据放用户目录 | 生成/持久化/轮换、实际 Windows ACL、损坏配置拒绝；真实启动器和停机轮换后旧密钥失效、记录保留 |
| 扩展升级 | 仅提交采集密钥；缺密钥不发送并保留队列，修正密钥后可恢复 | 状态机回归 + 真实扩展连接受保护 API |
| 界面会话 | 管理密钥只留内存；断开和 401 清空数据，旧响应不能恢复会话 | 客户端测试 + 真实生产页面配对/失效场景 |
| 页面备份 | 有版本与损坏校验、字段范围明确、10,000 条 / 20 MiB 上限 | 真正下载 JSON、敏感凭证排除、容量与历史坏记录拒绝 |
| 删除/恢复 | 明确确认、单事务修改原始与派生数据；恢复失败回滚 | 删除/重建、七类损坏备份、第二条写入失败的五表回滚 |
| 操作竞态 | 单进程所有权、API 数据操作串行化；旧分析先完成再删除其产物 | 第二进程拒绝、在途分析与删除竞争 |
| 资源边界 | 64 KiB/10 MiB/20 MiB 请求限额、10 秒读取总时限、4 个入口槽位、忙时 503 | 分块请求、并发入口、操作锁超时、CORS 错误可见性 |
| 可重复工作流 | Windows CI 增加真实前端配对和恢复流程，保留扩展实际采集验收 | 工作流静态检查、隔离数据库/浏览器执行 |

## 自我复查额外修正

- Windows 密钥 ACL 使用系统 .NET 文件接口一次替换权限，避免先重置为较宽的继承权限；同时避开部分 PowerShell 环境下 Set-Acl 模块自动加载失败。测试读取真实 ACL，确认无继承且只有当前用户和 SYSTEM。
- 备份按游标逐条检查容量，避免先把全部大记录装入内存再发现超限；超大记录 ID 不再溢出 SQLite 参数类型。
- 断开或认证失效时清空界面；客户端请求中止后仍检查会话代际。数据管理错误文案不声称超时必然回滚。
- 本机请求改用浏览器原生 fetch，并移除不再使用的 Axios 依赖。
- 禁止多进程共用同一数据库，避免只依赖进程内操作锁却遗漏跨进程竞争。
- 未开始发送响应的内部错误统一返回不含异常内容的 500，并保留允许来源的 CORS 与 no-store；恢复写入故障同时验证错误响应及事务回滚。
- README 明确默认路径变更、旧数据不会自动迁移、密钥重配、真实备份范围和重复采集边界。

## 与严格企业级发布标准的差距

**当前结论：工程基础明显加强，仍属于开发预览。** 不能用“测试全过”推导“全部环节绝对无 bug”，也没有可诚实给出的企业级完成百分比。下一轮按下表阻断顺序推进更有价值。

| 优先级 | 仍未完成 | 可验收的下一步 |
| --- | --- | --- |
| 发布阻断 | 仓库仍跟踪旧 SQLite、根 node_modules；缺根许可证与第三方许可清单 | 审计随附及历史内容，清理当前树，确定授权策略，生成不含私密数据的发布包；历史重写需另行明确范围 |
| 发布阻断 | 模型真实推理/训练环境、准确性、偏差和离线可用性未验收；旧分析接口仍有降级语义 | 固定模型/依赖/来源与基准数据；明确成功/失败状态并做真实推理验收；保持实验标签 |
| 高 | 隐私管理仍不完整：逐站授权、保留周期、加密备份、损坏队列导出修复没有完成 | 更细权限与可解释删除范围、自动保留策略、凭证/备份治理、恢复演练 |
| 高 | 记录按 URL 去重，没有访问事件、阅读时长或内容版本 | pages/visits 分离、稳定事件 ID、版本化数据库迁移与回滚 |
| 高 | 分支检查尚未形成强制治理，缺发行签名、升级/回退工具、安全报告流程 | 必需检查与评审、签名可回退制品、变更记录和安全响应流程 |
| 高 | Python 只固定直接版本；缺完整锁文件、SBOM、持续漏洞扫描 | 分平台可复现依赖、依赖更新策略与风险处置门槛 |
| 高 | 分析占用时串行服务会延后采集；没有硬执行超时、进程级资源隔离 | 后台任务与取消、CPU/内存预算、容量/长期运行/断电及磁盘不足演练 |
| 中 | 前端体积大、beta 构建链，缺读屏和复杂页面性能验收 | 稳定工具链、按需图表导入、无障碍和性能预算 |
| 中 | 备份上限内有效，超限/不兼容历史库缺迁移向导 | 版本化迁移、容量内外恢复计划、旧库无损验证工具 |

本轮加强的是本机权限和恢复底线，未引入账户、多租户或云部署；这符合当前本地分发目标。架构继续使用单机 SQLite 和轻量 API 有合理性，不需要仅为“企业级”标签增加微服务。

## 当前优点

1. 采集密钥与管理密钥分权，扩展通常无需持有全库管理能力。
2. 默认数据离开仓库，基础记录流程不依赖模型下载；可信统计与实验分析继续分开。
3. 恢复、删除和旧请求竞争具有明确事务/并发语义，故障场景已经转成回归用例。
4. 同时验证 API、状态机和真实界面/扩展链路，形成下一轮可复用的验收基础。

详细安全假设、升级与恢复限制见 [本机访问与恢复边界](local-security-and-recovery.md)。

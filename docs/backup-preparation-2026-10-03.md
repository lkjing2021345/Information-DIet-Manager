# 备份准备阶段的资源边界（2026-10-03）

本轮仅修改后端备份准备和数据库连接的可选等待参数。前端视觉、备份字段顺序、`idm-page-records` v1 格式、规范化 SHA-256、下载文件名和恢复接口保持原约定；备份仍最多 10,000 条，完整 JSON 文件（含外层元数据）最多 20 MiB。

## 修复依据

旧实现 `SELECT *` 后才选择备份字段。对独立合成数据库的测量中，一个不参与备份的 4 MiB `content_hash` 使 Python `tracemalloc` 峰值从约 0.01 MiB 增至 4.01 MiB，尽管输出仍只有 347 字节。另一个包含 500,000 个整数的约 3.5 MB 原始 `meta` 会先被 JSON 解码，Python 峰值约 27.35 MiB，然后才因不符合字段约束返回 409。这些数字仅是该合成样本的 Python 分配测量，不包含 SQLite 原生内存，也不是进程总内存上限。

原有 20 MiB 输出限制因此不能约束读取异常旧行的瞬时分配，准备阶段也没有自身截止时间。

## 当前行为

- 在同一个 SQLite 读取事务内，先按 `id` 升序查询行编号和备份字段的合计存储字节数，再读取通过预算检查的明确字段。不会将 `content_hash`、`url_hash` 等无关列加载到 Python。
- `MAX_BACKUP_ROW_BYTES = 128 * 1024` 限制全部备份字段的合计字节数，使用 SQLite `length(CAST(field AS BLOB))` 计算，空值计零，包括旧库中异常类型的 `ts` 和 `source`。超过预算返回 413，发生在完整字段进入 Python、`tags`/`meta` JSON 解码之前。128 KiB 恰好相等可以进入后续正常校验。
- `BACKUP_PREPARE_SECONDS = 15` 是协作式准备截止时间。连接建立前、SQL 扫描、逐行读取、JSON 解码/模型校验、逐行编码、汇总摘要和最终编码均有检查。SQLite progress handler 每 1,000 条虚拟机指令检查截止时间；异常或成功后清除处理器并关闭连接。
- SQLite busy handler 不调用 progress handler，因此备份建立连接和每次查询/取行前都将锁等待限制为剩余准备时间与默认 5 秒的较小值。其他调用 `get_conn()` 的默认 5 秒等待不变。初始化 PRAGMA 或事务回滚异常时，连接仍会关闭。
- 准备超时返回 503、固定详情 `Backup preparation timed out; retry later` 和 `Retry-After: 5`。其他 SQLite 操作不可用返回安全的 503 重试信息。预算内的无效旧记录仍返回 409；记录数、行字节或最终文件超限返回 413。失败前不会发送成功下载头。
- 已完成快照的两个共享下载名额、64 KiB 分块、30 秒发送截止，以及取消后等待同步工作线程结束再释放资源，继续使用上一轮的交付实现。

## 明确的兼容性和能力边界

128 KiB 是新增的原始存储行限制。当前模型合法字段的常规 JSON 存储，包括最大长度的 Unicode 字段和 ASCII 转义 JSON，在该预算内。极端旧数据可能含大量 JSON 空白或冗余转义，解析后虽很小，但原始存储超过 128 KiB；此类数据现在明确返回 413，不能声称所有历史可接受输入都保持可接受。

20 MiB 仍是完整下载文件的限制，**不是进程 RSS 上限**。备份保留经过字段和总量限制的 Python 记录列表、摘要编码及最终 `BytesIO`，存在对象和编码开销；它尚未改为全程磁盘流式构建。

准备截止通过 SQLite progress callback、锁等待上限和阶段检查协作执行。它不能强制中止操作系统调用、Python/C 扩展中的单个计算阶段或不可调度的线程，不能宣传为精确 15 秒的硬实时终止。Windows 本地运行和外部程序持有数据库锁的场景由合成回归覆盖；未读取个人数据库或执行模型推理。

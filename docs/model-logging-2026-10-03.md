# 模型辅助模块日志路径修复（2026-10-03）

本轮只修改共享日志工具及其合成回归，不修改分类、情感、相似度、评估、训练或 Hugging Face 配置逻辑，不下载模型，也不读取已有个人日志。

## 已确认的问题

`src/lsj/src/algorithms/utils/logger.py` 原先直接执行 `Path(log_file)`。七个调用模块都传入 `../../logs/<模块名>.log`，因此写入位置由进程当前目录决定。从本仓库根目录计算该路径会指向工作区外的 `D:\logs`；在算法目录运行时则落到 `src/lsj/logs`。

独立临时目录探针使用两个不同工作目录和不同合成 logger 名，确认相同参数实际创建了两个不同祖先目录中的日志文件。对目录创建注入 `PermissionError` 时，该异常直接逃逸日志初始化。API 在运行实验性分析时导入这些模块，因此文件日志初始化失败也可能使分析不可用。这是源代码调用链与日志工具的验证，不是实际模型推理验收；没有尝试写入或检查真实 `D:\logs`。

## 当前行为

- 相对 `log_file` 仅使用文件名，写入 `%LOCALAPPDATA%/InformationDietManager/logs/`。旧的七个调用点文件名互不重复，无需修改业务模块。相对参数中的父目录或子目录不再选择日志位置。
- `LOCALAPPDATA` 缺失或为空时，使用当前用户的 `~/.local/share/InformationDietManager/logs/`。默认位置采用与后端默认数据库相同的应用数据目录约定；日志工具额外将空环境变量视为缺失，避免落到当前目录。
- 调用者显式传入绝对路径时仍使用该位置。支持中文路径，日志使用 UTF-8。
- 创建日志目录或打开文件遇到 `OSError` 时，不再让文件日志故障阻断模块导入。启用控制台时使用原有控制台处理器，按当前日志级别输出固定消息 `File logging is unavailable; using console logging.`，不包含目标路径、原始异常或 traceback。
- `console=False` 且未建立文件处理器时安装 `NullHandler`，避免 Python 的 `logging.lastResort` 意外输出。没有指定文件且禁用控制台时也保持静默。
- 正常的日志级别、格式、控制台开关与文件追加行为保持原约定。对已经配置的同名 logger 再次调用不会增加处理器，仍可更新日志级别；路径、格式和处理器不热切换。这延续原来的顺序重复调用合同，不宣称通用并发重配置能力。

## 验证与范围

`src/lsj/tests/test_logging_configuration.py` 的 13 项回归全部通过：两个工作目录写入同一用户日志目录、中文路径和内容、显式绝对路径、缺失/空环境变量回退、目录和文件权限失败、真实非目录冲突、控制台关闭、重复配置与正常格式/级别。

测试只加载标准库依赖的日志工具，使用独立合成 logger 名和自动清理的临时目录；所有文件处理器在测试结束时关闭。没有导入模型或访问现有个人日志。

后续配置复核补齐了纯空白 `LOCALAPPDATA` 的情况，沿用与数据库一致的用户目录回退；非空合法路径内容不裁剪。此前 Windows 会拒绝纯空白目录，导致文件日志降级而非成功落盘。新增空格/控制空白两项回归后，日志配置测试为 15 项。

本轮不新增日志轮转、保留期限、日志内容脱敏或环境配置，也不移动、删除旧日志。旧的手工历史提取脚本 `utils/fetch_data.py` 仍直接使用 `../../../logs` 和 `logging.basicConfig`；它不在当前 API 模型导入链中，本轮未修改。文件打开后发生的磁盘故障、真实模型日志内容和真实推理环境不由这些测试证明。

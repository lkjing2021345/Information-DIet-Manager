# 数据库二次清理错误的优先级

## 已确认缺陷

导出和备份的读取事务内会检查记录与输出预算。超限本应返回 `413`，不兼容数据本应返回 `409`。原 `get_conn()` 在传播这些错误时直接执行 `rollback()` 和 `close()`，清理自身再抛出普通异常就会覆盖最先发生的错误。

在临时 SQLite 数据库和真实 ASGI 路由上，给 `sqlite3.Connection` 的回滚或关闭方法注入 `OperationalError`，可以使单行预算超限从 `413` 变成带 `Retry-After` 的 `503`。这是确定性的双故障注入；没有耗尽磁盘、读取个人数据库，也不代表真实存储设备必然以这种顺序失败。

## 修复约束

- 连接作用域先保留最先发生的业务、初始化或提交错误，再尝试回滚和关闭。普通二次清理异常不覆盖原错误。
- 无论回滚是否失败，都尝试关闭连接。回滚过程中出现 `KeyboardInterrupt` 等系统级中断时仍尝试关闭，不额外吞掉该中断。
- 正常完成后的关闭失败仍向上传播；提交失败仍是失败。不能为了保持原错误而把单独的存储失败变成成功响应。
- `init_db()` 与普通连接使用同样的清理规则；初始化 SQL 中的显式事务和普通连接的提交位置保持不变。
- 不记录原异常文本或增加可能包含数据、路径和凭据的日志。未修改接口错误文案、资源预算、数据结构或前端。

尝试关闭并不等于证明故障设备已经释放所有资源；提交失败或客户端连接中断也不能证明数据一定没有写入。实际磁盘满、设备故障、断电和强制终止恢复仍是独立的验收项。

## 验证口径

回归使用临时 SQLite、真实事务和受控故障，检查 HTTP 错误类别、首个异常、回滚后的数据、连接关闭尝试及解除故障后的恢复。完整测试、隔离浏览器和提交后 CI 结果记录在 [质量状态](quality-status-2026-10-03.md)，不把故障注入等同于真实硬件故障验收。

新增 24 项回归，并修正原备份准备测试中意外依赖旧错误覆盖行为的一处预期。最终测试放到旧 `db.py` 实现的独立进程中为 **21 失败、6 通过**（包含原有连接定向 3 项）；修复后连同初始化和备份准备为 **70 项通过**。独立复核另跑 **47 项通过**及 5 个取消/系统中断探针，未发现新增阻断；这些重叠测试结果不相加。

HTTP `409` 的故障夹具使用非有限数 JSON，确实触发现有编码拒绝。普通格式损坏的 `meta` 在旧导出中存在宽容行为，不能用它冒充本批次的 `409` 复现。关闭失败夹具先执行真实 `close()` 再模拟错误报告，因此能验证异常优先级，但不证明任意底层关闭失败都能释放句柄。

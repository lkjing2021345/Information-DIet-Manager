# 训练 HTTP 关闭失败状态保护

本批承接 [HTTP 延迟分配](collector-http-lifecycle-2026-10-03.md)，修复应用自身在重复关闭时误认为已恢复、清除 HTTP 引用的问题，不承诺修复第三方底层资源释放。

## 缺陷与行为

锁定 HTTPX 0.28.1 的真实客户端配合合成 `AsyncBaseTransport` 确认：首次 `aclose()` 进入底层清理时，客户端可能已经将自身标为关闭。底层清理抛异常或被取消后，再次调用公开 `aclose()` 可能直接返回，不再触发底层清理。旧包装器据此清除引用并正常返回。并发关闭也有同类问题：第一个调用尚在等待底层清理，第二个调用就可能提前正常返回并清除引用。

现在两个 `BaseModelClient` 使用关闭锁与保留的失败标记：

- 首次调用开始便禁止新的生成。只有一个调用可以执行底层 `aclose()`，其他调用等待其结果。
- 首次底层关闭异常或取消仍原样向上传播，保留相同 HTTP 引用，并标记关闭失败。
- 失败后再次关闭不会重新调用 HTTPX，也不清除引用，而是抛出固定 `RuntimeError`：`Model client cleanup previously failed; resource state is unknown.`，不附带原异常正文或异常链。
- 正常关闭完成后清除引用；并发等待者和后续重复调用正常返回，不再次调用底层清理。未使用的客户端关闭仍不分配 HTTP。
- 取消等待关闭锁的调用只取消该等待者；它不取消实际执行关闭的调用，也不把正常关闭污染为失败状态。

模型池遍历全部客户端并保留本次首次关闭异常、收集器业务首错和取消传播、CLI 安全错误输出继续沿用原逻辑。请求、生成重试、置信度、派发和前端均未修改，没有后台清理任务、嵌套事件循环或对 HTTPX 私有 transport 的访问。

## 验证

新增 `test_collector_http_close_state.py` 12 项，使用真实锁定 HTTPX 客户端、合成 transport 和临时文件句柄，不建立网络连接或使用真实模型。覆盖双工具的异常/真实任务取消、顺序/并发重复关闭、正常并发关闭，以及等待者取消。测试明确检查真实 HTTPX 的公开 `is_closed=True` 不等于底层释放完成。

同时更新既有生命周期测试的 8 项故障分支，撤销旧的“可重试替身成功即允许包装器恢复”契约；即便替身具备重试能力，包装器也保留失败状态。其他 25 项正常和故障对照保持通过。

- 两文件合计 45 项对修复前源码实测：**20 failed / 25 passed，1.73 秒**。
- 最小状态保护修复后：**45 passed，0.99 秒**。
- 与并发配置、持久化故障、日志隐私、恢复计数和停止边界联动：**165 passed，10.42 秒**；`git diff --check` 通过。

独立复核、完整回归和精确提交 CI 由总验收另行记录。临时句柄由测试夹具在结束时直接关闭，这属于测试资源清理，不是生产依赖失败恢复的证据。

冻结后独立复核两文件 45 项通过（0.80 秒），池遍历和业务首错另 6 项通过（0.37 秒）。自拟实际 HTTPX + 合成 transport 的 8 组成功、异常、执行者取消和等待者取消全部通过；两工具 OpenAI/local 共 4 组自有本机 HTTP 请求也通过，每组 4 请求只使用 1 客户端，正常关闭后服务连接归零。全部禁用代理并使用自有临时资源，没有真实模型推理。

## 兼容与剩余边界

正常生成、首次关闭异常类型、未使用即关闭和正常重复关闭接口不变。故障后再次 `close()` 的行为有意收紧：不再尝试恢复，而是持续报告清理状态未知；它可能将首次取消之后的再次调用报告为固定 `RuntimeError`。首次取消仍为原来的 `CancelledError`，不会被替换。

保留失败状态和引用只保证应用不误报恢复，不代表底层故障资源已释放，也不提供通过 HTTPX 公开接口认定恢复的办法。继续生成需要新客户端实例，但不能因此把旧实例的资源记为已回收。实际故障回收、非合作 transport、任意重复取消/进程强杀和多事件循环共享仍需独立方案及验收。本批没有绕过依赖内部状态或增加自动清理重试。

首次关闭异常按照既有调用契约原样上抛；如果外部调用方打印其 traceback，可能包含底层异常内容。本批的固定安全错误针对后续调用，不应推广为任意外部异常打印都安全。

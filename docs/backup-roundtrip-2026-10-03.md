# 版本化备份恢复保留正文

日期：2026-10-03。合同为服务生成的 `backup.items` 经恢复、再次备份后语义相等；不承诺原 SQLite 文件字节或内部 ID、创建时间不变。

## 已确认的问题

临时合成数据库中存在 1500 字符的合法历史正文时，`GET /data/backup` 正常返回完整正文和有效校验和；将该服务生成的原包提交给 `POST /data/restore`，接口返回 200 和正确恢复数量，但再次备份只剩 1000 字符。当前备份数据类允许 2000 字符，既有预算测试也明确允许导出该上限的历史正文。

原因是恢复复用了普通采集的行转换函数。它不仅截断长正文，还会去掉首尾空白，把 `null`、空字符串和纯空白正文替换成标题。因此问题同时影响缺失值语义、原始空白和合法长正文，不是字符编码或校验和失败。

## 实现

`_row_from_item()` 和 `insert_items()` 新增仅供内部调用的 `preserve_text` 选项，默认关闭。只有通过版本、条目 schema 和校验和检查的版本化恢复路径显式开启，正文直接使用验证后的 `item.text`，保留 `null`、空字符串、纯空白、换行、首尾空白及 2000 字符以内全文。

普通 `/collect` 和 `/import` 继续执行现有正文清理、标题回填和 1000 字符截断。恢复仍在原事务中清空旧记录及派生结果、插入新记录并重新计算哈希和本地字符片段向量；重复规范化 URL 或中途失败依旧回滚。内容哈希使用实际保存的完整正文；向量输入仍遵循已有的 1000 字符预算，不扩大模型或计算范围。

没有改动备份格式、版本、校验和、行数/字节预算、鉴权、确认头、取消归属或前端。标题与 URL 在备份导出时已经经过数据类规范化，本批不把这种逻辑备份描述成原数据库字段的逐字节复制。

## 合成回归

新增 `src/hyh/tests/test_backup_roundtrip.py` 共 43 项，全部使用真实应用 API、临时 SQLite、实际备份文件内容和实际恢复事务：

- 27 项完整字段往返：9 种正文（缺失、空串、纯空白、未修剪正文、999/1000/1001/1500/2000 字符）分别配合 3 组合法可选值，覆盖空值、空集合、空字符串、Unicode、嵌套 metadata 及时间戳两端点。备份由服务自己生成，同一原包连续恢复两次，比较全部页面字段、内容哈希及重建向量数量。
- 12 项普通采集/导入兼容：原来的空正文回填、空白清理和 1000 字符截断保持不变。
- 1 项长正文恢复后清理派生结果、移除多余记录并重建向量。
- 3 项失败回滚：重复规范化 URL、第二条向量写入后的合成存储错误、校验和错误；逐表检查记录、向量、派生分析与修订号没有变化。

同一组新测试在旧实现上为 **22 failed / 21 passed**；修复后与既有恢复取消、备份准备预算、数据安全和摄入合同联合运行 **191 passed / 1 条既有 Starlette 警告，35.37 秒**。没有用手工伪造备份或假 HTTP 响应代替服务实际输出。整体回归、独立复核及精确提交 CI 由本轮验收记录补充。

测试中的本地字符片段向量是应用原有的确定性算法，没有真实模型推理、远程调用或个人浏览数据。实际断电、磁盘满、历史未知结构迁移仍不在本批证据范围内。

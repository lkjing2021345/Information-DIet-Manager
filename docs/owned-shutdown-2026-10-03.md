# 写入任务与停服所有权（2026-10-03）

## 已确认的问题

仅让请求在取消后等待 `asyncio.to_thread()` 不足以保护停服过程。当前锁定 Uvicorn 的 `Server.shutdown()` 在优雅等待超时后取消请求任务，随后立即结束应用 lifespan，并不继续等待这些请求。旧 lifespan 会因此释放数据库进程锁，而后台恢复或分析线程可能仍未结束。

另一个边界是 `asyncio.run()` 清理时取消所有 Task：`create_task(to_thread(...))` 包装的工作任务本身也会被取消，即使它的请求调用者使用了 shield；底层操作系统线程仍继续运行。不能把包装任务结束当成线程结束。

## 当前实现

- 每次应用 lifespan 创建独立 `WorkOwner`，不建立跨事件循环的全局任务列表。HTTP 中间件在首次等待前捕获该 owner，避免等待请求体或锁的旧请求误用后续 lifespan。
- `run_owned_sync()` 通过 executor Future 追踪实际线程完成，复制 ContextVar 上下文以保持原 `to_thread` 的传播行为。Future 不属于 asyncio 的 Task 集合，调用者始终 shield 等待它。
- 提交前检查关闭状态；检查、提交及登记之间没有异步等待。完成回调移除登记并检索异常，但不记录异常内容。
- lifespan 关闭时先停止接收新的后台工作，再等待所有已登记 Future。即使等待本身被重复取消，也在工作全部结束后才传播取消。等待在 `process_ownership` 内完成，之后才能释放 OS 数据库锁。
- 关闭期间已接收但尚未启动工作的请求返回固定 `503`、`Retry-After: 5`，保留 CORS 与 `no-store`；不提交新的线程。
- 请求取消仍由原请求等待线程完成，并负责关闭未交付的导出/备份对象。取消不承诺撤回已经授权的事务。六个普通写入路由另见 [写入取消说明](write-cancellation-2026-10-03.md)。

这套归属用于已经接入 `run_owned_sync` 的采集、导入、删除、恢复、轻量统计/摘要、两类模型分析以及导出和备份准备。健康、会话及普通只读列表/历史处理不因此宣称全部改成了后台登记。它不是模型硬执行期限或可强制终止的进程隔离方案：底层代码永久阻塞时，正常停服可能持续等待；操作系统强杀、进程崩溃和断电不在保证范围内。

## 验证

新增 `test_owned_shutdown.py` 的 10 项回归使用锁定 Windows CPython 3.12 环境：

- 直接执行已安装 Uvicorn 的真实 `Server.shutdown(timeout_graceful_shutdown=0)`，走超时、取消请求、结束 lifespan 的真实顺序；ASGI 应用、替换事务及 SQLite 都是真实实现。省略网络 socket 建立与系统信号发送，不能描述为完整操作系统停服演练。
- 暂停恢复线程时启动另一独立 Python 进程争用真实数据库锁：仍被拒绝；提交/回滚和连接关闭后该进程可以拿锁。分别覆盖线程成功/异常以及重复取消停服任务。
- 模拟 `asyncio.run` 对全部其他 Task 的取消，验证线程完成前请求和 drain 都不会退出。
- 单线程池被占用、工作尚未执行的排队情形同样保留归属；ContextVar 传播、关闭后拒绝提交、同一循环两个 owner 独立、两次事件循环无残留，以及等待请求体期间 owner 被替换时的隔离均通过。

定向结果 **10 passed**（4.27 秒）。只用临时路径、合成记录和测试密钥；没有读取个人数据库或执行模型。完整回归、真实浏览器及精确提交 CI 结果在质量状态报告中单列。

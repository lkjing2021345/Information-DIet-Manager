# 导出与备份的小负载工作集测量

这是 2026-10-03 本机探索性测量，补充此前仅有的 Python 分配统计，不是性能预算验收。测量使用 `b8b7507` 后的工作目录和生产准备函数；并行进行的导出 JSON 读取修复不影响本探针的空 `tags` / `meta` 输入。没有独立、可发布的基准制品，原始探针与结果保留在被忽略的本地 `output/playwright/working-set-20261003/`。

## 方法和负载

每个样本在一个新的 Windows Python 子进程内创建临时 SQLite，使用当前 schema，插入 0、250、1000 或 2000 条合成页面。每条正文 900 个 ASCII 字符，URL 位于 `example.invalid`，标题、时间和来源也是合成值。每个大小分别运行一次普通 raw JSON 导出与一次页面备份，八个样本输入合计 6,613,180 字节，小于本探针的 8 MiB 输入约束。

调用实际 `export_io.prepare_export()` 或 `data_management._prepare_backup_response()`，核对完整产物的长度并关闭它，不经 TestClient 额外缓存响应体。环境为既有纯运行环境，14 个运行包版本与当前运行锁一致，没有 pandas 或模型；其 pip 仍为 24.2，因此不能将它描述为本轮从完整安装器锁重建的验收环境。

用标准库 `ctypes` 调用 Windows `GetProcessMemoryInfo`，读取 `WorkingSetSize` 和 `PeakWorkingSetSize`。这两项分别为当前和峰值工作集，单位字节，不是 `tracemalloc`，也不等于私有提交内存。[微软结构定义](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex)、[读取函数](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-getprocessmemoryinfo)

基线在造数与垃圾回收之后、准备函数调用之前读取。每个样本的新内核峰值均高于调用前已存在的生命周期峰值，因此该新峰值发生于本准备窗口；包含监测线程本身的开销。另以 5 ms 周期采样，但不以采样最大值替代内核峰值：2000 行备份的采样峰值为 50.535 MiB，低于内核峰值 52.609 MiB。

父进程以 256 MiB 工作集观察阈值和 25 秒超时限制探针，未触及任一阈值；它们是这次探针的保护约束，不是产品默认上限或实时资源限制保证。

## 单次观察值

MiB 按 1,048,576 字节换算；增量是准备期间内核新峰值减去调用前工作集。

| 普通导出 | 0 | 63 | 44.363 | 44.977 | 0.613 |
| 普通导出 | 250 | 285236 | 44.367 | 45.402 | 1.035 |
| 普通导出 | 1000 | 1141738 | 44.785 | 45.730 | 0.945 |
| 普通导出 | 2000 | 2286738 | 44.922 | 46.805 | 1.883 |
| 备份 | 0 | 156 | 44.473 | 44.625 | 0.152 |
| 备份 | 250 | 270685 | 44.703 | 46.340 | 1.637 |
| 备份 | 1000 | 1082935 | 44.918 | 48.980 | 4.062 |
| 备份 | 2000 | 2167935 | 44.609 | 52.609 | 8.000 |

这些观察与“普通导出逐行写临时文件、备份仍在进程内组装对象和编码副本”的实现一致，但每个点只有一次运行，不能作为可靠的扩展曲线或性能承诺。当前证据不包含完整 HTTP 请求、并发、慢消费者、ACL 子进程、系统文件缓存总量、模型、最大导出规模、20 MiB 上限备份或长期运行；仍须逐项验收。

# 训练收集器生成失败日志的内容保护

本批处理分类、情感收集器各自的 `ModelPool.generate()`、`_generate_one()`，以及后续复核确认的分类收集器 `_relabel_check()` 日志中的异常原文、模型响应预览和源文本。最后增补进度加载、SBERT 初始化、情感 PPL 初始化及历史嵌入的 7 处同类原异常日志；不改变生成结果、重试次数、正常标签、数据保存、调度或界面。

旧版在重试事件中记录 `str(e)`，最终错误又拼接该异常；生成失败记录原异常，无效 JSON 记录响应预览，标签不匹配时记录返回标签及文本片段。纯合成、无网络探针确认这些内容会进入实际 `log_event`，并由测试附加的真实控制台和临时文件处理器写出。收集器默认日志是否另被重定向保存取决于调用环境，本批不声称默认创建了这些测试日志文件。

现在保留事件、异常类型、重试信息、合法的预期标签以及响应／文本／返回标签长度，去掉上述原文和预览。模型池最终抛出固定的 `All models failed.`，并通过显式 cause 保留原异常，供直接调用者判断；这些已测日志路径不打印 traceback。合法生成记录的正文和标签原样保留。

新增 `test_collector_log_privacy.py` 最初 12 项覆盖两个收集器的可重试网络异常、一般异常、生成失败、无效响应、标签不匹配和成功响应对照。模型池、生成方法及日志分支使用实际实现，客户端／响应为替身，没有创建 HTTP 客户端、下载或运行模型，也未读取个人配置和浏览数据库。

- 旧版：**10 failed，2 passed，0.70 秒**。
- 修复后与收集器故障、恢复、追加格式、停止边界回归合计：**230 passed，11.05 秒**。
- `git diff --check` 通过。完整回归和精确提交的 CI 由总验证记录。

后续独立复核又确认分类 `_relabel_check()` 的生成异常、解析失败与拒绝结果三个事件仍包含源文本、返回标签或响应片段，因此追加这三个分支及成功结果对照共 4 项。旧实现 **3 failed，1 passed，0.55 秒**；修复后全部 **16 passed，0.53 秒**。这一追加范围不由前述 12 项或 230 项证据覆盖。复核日志现在保留固定事件、异常类型、长度及原可信标签／置信度／模型名，返回值、源记录和传入模型的合成复核提示保持不变。

最后对仍含原异常的 7 处路径做有界验证并增补测试：两个 `ProgressTracker.load()`、两个 `_try_load_sbert()`、情感 `_try_load_ppl_model()`、两个 `_load_existing_state()` 的嵌入失败分支。这里仅将 `reason=str(e)` 改为异常类型，保留原 `progress_path` 和回退行为。增补测试旧版 **7 failed，0.47 秒**；修复后全文件 **23 passed，2.08 秒**。前述 16 项与 230 项结果不覆盖这 7 项增补。

进度文件使用真实 JSON 中的陌生字段触发自然 TypeError：证实旧日志回显字段名，字段值负对照未泄漏，不能把该证据称为配置值泄漏。初始化使用显式替代模块注入含合成配置标记的异常，没有导入真实模型或下载；只证明异常内容保护的缺口，不证明真实依赖通常会输出密钥。历史嵌入则真实读取临时训练文件，替身收到源文本后将它放入异常。增补同时验证有效进度加载、模型替身成功初始化、历史嵌入成功对照、失败返回语义，以及历史文件、记录数和标签数不变。

密钥只是插入替身响应／异常的合成标记，证明敏感内容一旦进入这些对象不会再被这些事件原样写出。另一个纯内存 HTTPX 503 对照表明，标准 HTTPStatusError 字符串不含 Authorization 头的合成密钥；没有发现项目把 API capability 自动发送给模型，也不据此声称普通 HTTP 错误会暴露所有 API key。

保证范围仅限上述方法的已测通道，其他配置解析等日志没有完成全面隐私验收；直接调用者自行打印保留的异常 cause 仍可能暴露原文。本批不是整个收集器日志安全或真实模型质量的完成证明。
